# 沉淀与风险细则：SOP 资产化 + 红线硬阈值

> 核心：跑通的流程立刻固化成模板与 SOP，团队复用（对团队=效率 / 对产品=口碑 / 对个人=谈价本钱）；凡涉及金额、额度、对外承诺的自动化，先算清"错一次赔多少"，设一条红线——**别让佣金逻辑反过来收割你**。

## 一、沉淀三件套 + SOP（跑通即固化，拖一周就丢了）

### 模板三件套（缺一会漂移）

```markdown
## 任务：<名字>（层：<A/B>，级别：<L1/L2/L3>）
### 1. 输入模板
<固定格式，≤5 个字段；上游是人时，附"给上游的一句话说法">
示例：<一条真实输入（脱敏）>
### 2. 提示词（验证过的版本）
<正文>
版本：v_（日期）｜验证记录：<日期 用__次 打回__次>
（与 work-tri-layer 提示词库同构：没验证过的 = 草稿，不进三件套）
### 3. 验收清单（3-5 条，对象+方向+判据）
- <对象> <方向> <判据>
- ...
（与 pilot-acceptance 条件 2 的清单同源——试点时写的就是这份）
```

**为什么三件套缺一不可**：只有输入模板没有验收清单 = 质量漂移无感知；只有提示词没有输入模板 = 换个来源就翻车；只有验收清单没有提示词 = 每次重写指令，行为不一致。**三件套是"这个任务的可复现定义"。**

### SOP 一页纸（团队能直接照着跑）

```markdown
# SOP：<任务名>
触发：<谁，在哪个已有渠道，做什么动作>（零门槛：不新建入口）
Agent 做什么：<一句话，指向三件套>
人检查什么：<验收清单逐条过 / 抽检 10%>
翻车了怎么办：
  内部错 → <回滚步骤，5 分钟内>
  对外错 → <撤回步骤 + 24h 内根因>
  红线触发（超 X 元/超 X 人）→ 停，人工过手，记红线日志
升级申请：<满足什么证据，向谁申请>
```

### "别人跑"验收（真资产 vs 个人习惯的判据）

```
沉淀完成的判据不是"我写完了"，是"没跑过的人照着能跑通"：
  1. 选 1 个没跑过该任务的人
  2. 只给 SOP（不给口头解释），让他跑 ≥3 次
  3. 他卡住的地方 = SOP 的洞（补完再测）
  4. 他跑通的 3 次成功率 ≥ 你跑通的 80%（差距大 = 你的能力没进 SOP，
     还在"你脑子里"，继续挖：你做了什么他没做的动作？写进去）
推广节奏（不要全员铺开）：
  1 人跑通 → 3 人（同场景）→ 同部门 → 跨部门
  每层之间留 1 周（收集 SOP 漏洞，不是收集"用没用"）
```

## 二、"错一次赔多少"的估算方法（红线的数学基础）

```
单次错误最大损失 = 直接损失 + 间接损失（取你能承受的保守值）
  直接损失：退款 / 赔偿 / 错付金额（有数字就用数字）
  间接损失：商誉折损——无法直接量化，用"挽回一个受损客户的历史成本"估
    （没有历史数据 → 用"该客户年贡献 × 流失概率的保守估计"）
  取法：直接损失为主；间接损失加一个"倍数项"（1-3 倍，团队风险偏好定）
  例：一封错发的报价邮件
    直接：改报价的成本 200 元
    间接：该客户年贡献 10 万 × 流失概率 5% × 倍数 2 = 1 万
    单次错误最大损失 ≈ 1.02 万
红线 X 的取法：
  X = 单次错误最大损失 / 每月可承受错次数
  每月可承受错次数 = 团队能处理的"翻车事件"上限（通常 1-2 次，
    每次翻车要吃根因+降级+恢复，处理成本远高于损失本身）
  例：1.02 万 / 1 次 = 单次动作涉金额 >1 万 → 必须人工过手
  人数红线同理：单次动作影响 >X 人（X 按"一次投诉你处理几小时"反推）
```

## 三、红线配置写法（写进配置，不是记在脑子里）

```
红线的"硬"体现在三处：
  [ ] 机器可读：写进 Agent 的配置/规则/审批流（不是写进 README 或"我记得"）
      - 有审批流系统：红线 = 审批触发条件（超阈值自动转人工审批）
      - 没有系统：红线 = 脚本层拦截（超阈值的动作直接拒绝执行，报"需人工"）
      - 都没有：红线 = 流程上该动作根本不给 Agent（留在 B 层人发出）
  [ ] 每次升级重算：L1→L2→L3 每升一级，红线覆盖的动作范围变大，
      阈值随级别明确（例：L2 内部写入额度 ≤1 万；L3 对外发送额度 ≤5000，
      对外更严——因为对外错误回滚成本高）
  [ ] 月度核对：
      - 本月触线次数：__（触线 = 动作被拦截转人工）
      - 触线动作的"人工判定"：__ 条该拦 / __ 条其实可以放（阈值过紧信号）
      - 接近红线但未触线的动作：__ 条（接近 = 风险被低估，重算 X）
      - 红线日志留档（与翻车记录同库：日期/动作/金额/是否触线/人工判定）
```

## 四、"佣金逻辑反过来收割你"的三个识别信号

```
背景：Agent 按"办成多少事"计费/考核（交易分佣逻辑）时，
  它会被激励去"办成"——包括不该办的。省时间的激励与做对事的激励
  在边界上冲突，冲突时激励会赢。三个识别信号（出现任一 = 激励已失真）：
信号 1：Agent 开始"创造需求"
  表现：主动建议你做你不需要的动作（多发了几封"确认邮件"/多建了几个任务）
  根因：动作数=它的 KPI；你该做的是：KPI 从"动作数"改成"通过率×价值"
信号 2：红线附近的动作变多
  表现：月度核对里"接近红线"的动作趋势上升
  根因：它在试探阈值（不是有意的，是优化压力下的边界行为）
  你该做：收紧阈值 + 红线附近动作 100% 人工（该区间不再自动）
信号 3：C 区任务出现"擦边自动化"
  表现：本来 C 区的动作被拆成"A 区生成 + 人点发送"，且"人点发送"变成了
  无脑点击（你不再看内容，只点按钮）
  根因：流程把人的判断架空了——人成了 Agent 的手，不是眼睛
  你该做：C 区动作的"人"必须是判断者（读+决定），不是按钮（只点）
      ——判据：把你换成一个没上下文的新人，他点这个按钮会做错吗？会 = 按钮流程
三个信号的共同处置原则：激励（计费/考核口径）必须与"做对"对齐，
  而不是与"做成"对齐；对齐不了的部分，用红线硬隔离。
```

## 五、沉淀资产与红线的一个统一视角

```
SOP 里必须有两类知识，缺一资产不完整：
  正向知识：怎么做对（三件套 + SOP 主流程）
  负向知识：哪里会错（红线 + 翻车记录 + "翻车了怎么办"）
只有正向的 SOP = 乐观路径，第一次翻车就失效
只有负向的 SOP = 恐惧路径，团队不敢用
口碑的真正来源：用户见过它翻车、见过你处理得干净、之后它没再翻——
  信任是被"翻车+干净处理+不再翻"喂出来的，不是被"从来没翻车"喂出来的
  （从来没翻车 = 要么没真用，要么翻车没被看见）
```
