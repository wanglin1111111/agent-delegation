# 单点试点细则：任务选择、四条件、两周验收

> 核心：只挑一个**高频、低风险、结果可验证**的任务开刀，两周试点，验收只看两个数——成功率、省下多少分钟。**不靠感觉判断好不好用。**

## 一、任务选择排序（从分层表里选）

```
候选池：A 层全部 + B 层里"模板化程度高"的
排序矩阵（三项各 1-5 分，加总分）：
  频次（越高越好）：≥10 次/周=5，5-9=4，3-4=3（<3 出局，摊不平成本）
  低风险（越低越好）：A 层=5，B 层模板化=3，B 层非模板=2
  可验证（越明确越好）：有客观判据（格式/字段/清单）=5，半客观=3，纯主观=1
选总分最高者；同分选频次最高的
反例（典型选错）：
  ✗ 选"最难自动化"的任务当第一个（验证的是 Agent 上限，不是你的工作流）
  ✗ 选"最高价值"的任务（价值高往往=风险高+验证模糊，违反低风险可验证）
  ✗ 选"最感兴趣"的任务（兴趣不是排序因子，频次才是）
```

## 二、可交接四条件（缺一条先补条件，不硬上）

### 条件 1：输入能结构化

```
检验：连续 5 次该任务的输入，长得一样吗？（来源固定？格式固定？字段固定？）
  一样 → 过
  不一样 → 补条件：做一周输入归一
    - 固定来源（只从这 3 个渠道收，其他渠道的输入先手动归一）
    - 输入模板（给上游一个固定格式；上游是人，模板要 ≤5 个字段，否则没人填）
  归一周后重检 5 次输入；仍不一致 → 该任务输入本质多变，换任务
```

### 条件 2：结果能验证

```
检验：能写出 3-5 条"怎样算做对"吗？（客观可判，不是"质量要好"）
  写得出 → 过（这 3-5 条就是验收清单，与 work-tri-layer 验收清单同构）
  写不出 → 补条件：先人工做 3 次，每次记录"哪里不对"，从返工原因反推清单
  清单全是主观词（"专业/清晰/到位"）→ 把每条改写成"对象+方向+判据"
    例："要清晰" → "第一段有结论，且结论 ≤2 句"
```

### 条件 3：出错能回滚

```
检验：Agent 做错了，你能在 5 分钟内撤销吗？
  能（删文档/改表格/撤回邮件未发送）→ 过
  不能（已对外发出/已付款/已提交）→ 该任务不可逆
    → 降为 B 层处置（Agent 起草，人发出）——"生成"可试点，"发出"不进试点
    或换任务
  回滚测试：试点开始前，故意让 Agent 做一次"错误产出"，实测回滚流程
    （没实测过的回滚 = 想象中的回滚，L2 阶梯要求必须实测）
```

### 条件 4：频次 ≥ 每周 3 次

```
检验：翻过去 4 周的实际记录（不是记忆），该任务发生了多少次？
  ≥12 次 → 过
  <12 次 → 补条件：
    合并同类（"每周 2 次客户邮件 + 每周 2 次供应商邮件" → "商务邮件回复" 4 次/周）
    或升频（把本来攒一周做的事拆到每天做——如果业务允许）
  仍 <3 次 → 换任务（低频任务的学习成本摊不平，试点两周也验证不出统计意义）
```

## 三、两周试点的逐日检查点

```
D1  开跑前：四条件复核签字（自己确认四条全过）；验收清单 3-5 条定稿；
     基线记录：手工做一次该任务，计时 __ 分钟（这个数后面要用）
D2-3  试跑：Agent 做，你按验收清单逐条检查；
     记录每天：成功/失败 + 失败原因（输入问题/标准问题/Agent 能力问题）
     纪律：检查时间计入"Agent 单次耗时"（漏掉检查时间 = 省分钟虚高）
D4  第一次归因：3 天数据看一眼
     失败率 >30% → 停，按归因树修（见下），修完重跑 3 天（试点顺延）
     失败率 <10% → 继续
D5-9  放量：全量交给 Agent（你只做检查）；
     每天记录：次数/成功/失败/Agent 耗时（含检查）
     中间检查（D7）：省分钟趋势 vs 目标 50%——落后 = 回查耗时结构
D10-13  稳定期：不修任何东西（暴露真实运行状态，不是调优状态）
D14  验收：算两个数（见下），写试点结论：
     过 → 进第 3 步零门槛接入 + 第 4 步信任阶梯评估
     不过 → 试点失败归因（任务选错 or 条件没补好），回第 1 步
```

## 四、两个数的计算与常见误算

```
成功率 = 验收通过次数 / 总次数
  目标 ≥80%（A 层；B 层看"你拍板后返工率"，目标 <10%）
  误算 1：把"Agent 重跑后对了"算成功（重跑=失败，重试成功也要记失败+重跑次数）
  误算 2：失败里"你的输入给错了"的不算失败（输入错是真实运行的一部分，
    除非你能证明输入归一已经做到位——归一后还错输入 = 条件 1 实际没过）

省下分钟 = (手工单次耗时 - Agent 单次耗时含检查) × 频次 × 2 周
  目标 ≥50%（低于 50% = 工具成本>节省，试点不算过）
  误算 3：Agent 耗时只算"生成时间"，不算你的检查时间（最大的虚高来源）
  误算 4：手工基线取"熟练状态"（D1 的基线要取日常真实耗时，不是最熟练的一次）
  误算 5：频次取"理想频次"而非实际（用 D2-13 实际发生的次数算）
两个数都要达标；只中一个：
  成功率达标 + 省分钟不达标 → 任务选错了（太简单，本来就没多少时间可省）
  省分钟达标 + 成功率不达标 → 检查成本太高（验收清单太细 or Agent 不稳），修清单或换 Agent 配置
```

## 五、试点失败归因树

```
失败（成功率<80% 或 省分钟<50% 或 两者）
├─ 输入问题（失败记录里"输入相关"占比 >40%）
│   → 条件 1 实际没过：归一没做到位 → 回补归一，再试点
├─ 标准问题（失败记录里"验收清单相关"占比 >40%：清单漏判/清单太严/清单模糊）
│   → 条件 2 没过：重写清单（从失败案例反推），再试点
├─ 回滚问题（试点中发生过"错了撤不回来"）
│   → 条件 3 没过：任务降 B 层处置或换任务
└─ 任务问题（以上都不是，Agent 就是做不好这类任务）
    → 任务选错：回任务分层表，按排序矩阵选下一个，重跑试点
      注意：连续 3 个任务试点都失败 = 你的 Agent 配置/选型有问题，
      不是任务问题——回查工具本身（与 pipeline-onboard 的"工具退化成批量上传器"同判据）
```
